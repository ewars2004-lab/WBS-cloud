# 新NagiWBS — 5W1H お客様目線ガイド（J〜O列）

WBS進捗表の **J〜O列**（When / Where / Who / What / Why / How）を書くときの正本。  
案件別スプレッドシートの **5W1Hタブ** とは別物（提出物・詳細設計向け）。WBS上は **進捗の要約** として、**お客様（会員・利用者）が何を体験するか** を軸に書く。

## 基本方針

| 列 | 書くこと | お客様目線のコツ |
|---|---|---|
| **J When** | いつから・いつまで追うか | 会話の起点日や、お客様に届くまでのマイルストーン |
| **K Where** | どこで（チャンネル・環境） | `#pj_XXXXX` や `stg` / 本番など、調査・確認の場所 |
| **L Who** | だれが | 社内担当＋**お客様（会員）が関わる役割**が分かるように |
| **M What** | なにを | **お客様が体験する変化・状態**（内部タスク名ではない） |
| **N Why** | なぜ | **お客様への影響**（遅れると困ること・直ると嬉しいこと） |
| **O How** | どのように | **お客様視点での検証・改善の進め方**（社内手順の羅列ではない） |

### 3つの軸（覚え方）

1. **What** = お客様体験（「お客様が〜できる／〜が直る」）
2. **Why** = お客様への影響（「〜だとお客様が困る／安心できる」）
3. **How** = お客様視点の検証・改善（「〜を確認する／〜を整える」）

### やらないこと

- 「要件定義をする」「FBをもらう」だけの **社内作業記述** で What を終わらせない
- エンジニア用語だけで Why を書かない（「バグ修正のため」→ お客様が困る具体を書く）
- 案件別 **5W1Hタブ** と同じ粒度・品質を WBS 行に求めない（要約でよい）
- Shuri人格チームの提出物向け5W1H基準は **適用しない**

## 案件トピックの取り方

A列（案件名）から **お客様が困っていること・変わる体験** を1フレーズで抜く。

- 例: `Myクローゼットアイテム購入したアイテムを削除する際に、アプリが強制終了してしまう`
- 業務系（物流・連絡品質）: 「お客様の荷物・連絡」目線に言い換える

## 工程別テンプレ（B列）

`{topic}` = 上記のお客様体験フレーズ。`{channel}` = K列のチャンネル。

### 5W1H / 5W1H修正

| 列 | 文型 |
|---|---|
| M | お客様が体験する「{topic}」の問題と、直したい状態が整理される |
| N | 問題の認識がずれると、お客様体験を直す修正の前提がぶれるため |
| O | 不具合の再現条件と、お客様にどう見えてほしいかを整理する |

### Figma作成 / Figma修正

| 列 | 文型 |
|---|---|
| M | お客様が体験する画面フロー（{topic}）の問題点と理想状態が図で明確になる |
| N | 図が不明確だと、お客様に誤った画面が届く修正になるため |
| O | 問題のある操作と、直した後にお客様にどう見えるかを図に反映する |

### 機能一覧作成 / 機能一覧修正

| 列 | 文型 |
|---|---|
| M | お客様体験に関わる機能要件（{topic}）の抜け・重複が直される |
| N | 要件のズレは、お客様に届く機能の漏れや誤動作につながるため |
| O | FBを反映し、お客様視点の機能・条件を表に整える |

### 総合テスト作成 / 総合テスト修正（#1 等含む）

| 列 | 文型 |
|---|---|
| M | お客様が実際に行う操作（{topic}）を再現するテスト観点が揃う |
| N | 観点不足だと、本番でお客様が不具合に気づく前に検知できないため |
| O | お客様操作手順・期待結果をテストケースに明記し、レビューを受ける |

### 総合テストの実施

| 列 | 文型 |
|---|---|
| M | お客様視点の操作で「{topic}」が直っているか確認される |
| N | 検証漏れは、お客様に不具合が残ったままリリースされるリスクがあるため |
| O | stg等でお客様と同じ手順を実施し、結果を記録する |

### リリース / リリース後テスト

| 列 | 文型 |
|---|---|
| M | 「{topic}」の修正が本番に反映され、お客様体験が改善される |
| N | 反映が遅れると、お客様が不具合を見続けるため |
| O | 総合テスト完了後に本番リリースし、稼働を確認する |

### インプットMTG / エンジニア見積もりMTG

| 列 | 文型 |
|---|---|
| M | 「{topic}」を直すための範囲と、お客様に届くまでの見通しが共有される |
| N | 認識ズレは、お客様への提供時期や品質に影響するため |
| O | 関係者で要件・工数を擦り合わせ、お客様影響を確認する |

### 開発進捗管理

| 列 | 文型 |
|---|---|
| M | 「{topic}」の修正が計画どおり進み、お客様に届く準備が整う |
| N | 進捗が見えないと、お客様への提供タイミングが不透明になるため |
| O | 開発状況を追い、お客様体験への影響を随時確認する |

## MD系（A列が MD / NOLLEYS / UNFILO 等）

お客様 = **エンドの購入者・着用者**。商品が届くタイミング・品質の目線。

| 列 | 文型 |
|---|---|
| M | MDの各工程が、お客様に届く商品計画と整合する（工程名に応じて具体化） |
| N | 工程の遅れ・ズレは、お客様向け商品の準備スケジュールに影響するため |
| O | BSOMDカレンダー塗りと照合し、お客様向けタイミングをWBSに反映する |

`MDを期日入れる` 工程:

- M: MDの各工程期日が、お客様に届くタイミングと整合するよう設定される
- N: 期日が不明だと、お客様向け商品の準備スケジュールがずれるため
- O: カレンダー塗りから期日をWBSへ反映する

期日の根拠は [md-calendar.md](./md-calendar.md)。

## 業務・物流系（例: 124304 / 123067）

不具合修正ではなく **お客様の荷物・連絡品質** 目線にする。

- M: お客様の配送・連絡体験が〜（具体の業務内容）
- N: 〜だとお客様の不安・問い合わせが増えるため
- O: 倉庫・CS連携でお客様向けの状態を確認・改善する

## Slack調査から WBS 列へ

Investigator の `inference.when/where/who/what/why/how` を Writer が J〜O に写すとき、上記テンプレに **会話の具体** を足す。  
会話に新しいお客様影響が出たら、M/N/O を更新してよい（E列が進行中のままでも可）。

## 品質チェック（Verifier 用）

- [ ] M に「お客様」またはお客様体験が主語・目的語として入っている
- [ ] N が社内都合だけで終わっていない（お客様への影響がある）
- [ ] O が検証・改善の進め方として読める（「Slackを見る」だけは弱い）
- [ ] B列の工程と M/N/O の文型が対応している
- [ ] 列ずれがない（J=When … O=How の6列）
